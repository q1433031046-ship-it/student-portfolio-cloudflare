# 学生作品展示｜部署与后台使用指南

> **部署前入口：本 GitHub 页面。**  
> **部署后入口：登录自己网站的 `/admin`，点击右上角“使用教程”。**
>
> GitHub 承担部署前的公开说明；每位学生部署成功后，由自己的 Cloudflare 账号承载前台和后台访问。模板不提供公共 `/guide` 页面。

---

## 一页看懂整个流程

**打开本指南 → 打开 GPT → 核对 GitHub / Cloudflare 账号 → 官方一键部署 → 创建管理员 → 编辑内容 → 快速预览 → 由发布角色激活唯一 Netlify Site → 正式发布静态网站。**

| 入口 | 用途 |
|---|---|
| GitHub 本页 | 部署前的中央指南与官方部署入口 |
| 学生网站 `/` | 对外展示的作品集前台 |
| 学生网站 `/admin` | 管理员后台，使用密码登录 |
| 后台“使用教程” | 登录后打开完整的站内教程 |
| 后台“程序升级” | 定位升级中心并复制升级指令 |

宽屏后台的“使用教程”“程序升级”在右上角；手机后台从底部操作栏打开“更多”，可进入这两个入口。登录后才能看到它们。

### 安全边界

| 可以发给 GPT | 只在官方页面或网站后台输入，截图也不能包含 |
|---|---|
| 遮住个人信息与秘密后的局部截图、按钮位置、项目名、仓库名、Worker 名、构建错误 | GitHub 密码、Cloudflare/Netlify 密码、管理员密码、`INITIAL_ADMIN_CODE`、系统恢复码、API Token、Build Hook、浏览器 Cookie、二维码、二维码访问链接 |

截图前只保留需要核对的按钮或错误区域，并遮住账号、资源 ID 和私人内容；二维码及其访问链接等同访问凭证，不进入聊天或截图。

## 1. 部署前准备

### 1.1 账号与设备

准备以下内容后再开始：

- 一个可正常使用的 ChatGPT 账号；
- 一个可正常登录的 GitHub 账号；
- 一个可正常登录的 Cloudflare 账号；
- 一个归当前学生所有、可恢复登录的 Netlify 账号；每个作品站只使用一个固定 Site；
- 一个能接收验证码的邮箱；
- 一台电脑，推荐 Chrome 或 Edge；
- 手机放在旁边，用于邮箱验证码或二步验证。

Google / Gmail 不是硬性要求。GitHub 和 Cloudflare 可以使用 Google、GitHub、Apple 或邮箱密码登录，关键是记清自己最初选择的登录方式。

建议先记录：

| 项目 | 自己填写 |
|---|---|
| GitHub 用户名 |  |
| GitHub 登录方式 | Google / 邮箱密码 / 其他 |
| Cloudflare 登录邮箱 |  |
| Cloudflare 登录方式 | Google / GitHub / Apple / 邮箱密码 |
| 这是该账号的第几个网站 | 第 1 / 2 / 3 个 |

### 1.2 部署不需要额外密钥

正常流程无需提前创建：

- OpenAI API Key；
- Codex API Key；
- Cloudflare API Token；
- GitHub Personal Access Token；
- 其他长期密钥。

### 1.3 素材建议提前整理

- 姓名；
- 职业标题和求职方向；
- 一句个人定位；
- 邮箱和电话；
- 首页首图；
- 项目封面；
- 项目简介、项目难点、解决思路；
- 项目过程图片；
- 可选的 H.264 / AAC 编码 MP4 成稿视频；作品没有视频也可以发布。

## 2. 先打开 GPT：每一步点哪里

### 2.1 打开 ChatGPT

1. 在电脑浏览器登录自己的 ChatGPT。
2. 点击“新建对话”。
3. 页面有“工作”模式时优先选择“工作”；没有时使用普通对话。
4. 后续 GPT 需要 Codex 检查仓库或修复构建时，可以允许相应操作。

### 2.2 选择模型和思考程度

- 能单独选择模型时，优先使用 **GPT-5.6 Sol**；
- 看不到单独模型选择时，保留默认 **Power** 即可；
- 一般部署使用默认思考程度或 **High（高）**；
- 资源绑定、数据库迁移、账号串号、版本冲突、复杂构建故障或升级，可按界面实际提供的选项提高到 **High（高）** 或 **Extra High（超高）**。

模型和思考选项会随账号界面变化；看不到某个精确名称不会阻止部署。

### 2.3 完整复制部署引导语

```text
我要部署“学生作品展示”网站。请全程一步一步带我完成，一次只让我做一个主要动作。

开始前请先确认：
1. 能单独选择模型时优先使用 GPT-5.6 Sol；看不到单独模型时保留默认 Power。一般部署使用默认或 High（高）；复杂升级或故障时，按界面实际可用项提高到 High（高）或 Extra High（超高）。
2. 当前浏览器实际登录的是哪一个 GitHub 账号、哪一个 Cloudflare 账号。
3. 这是这个 GitHub / Cloudflare 账号里的第几个学生作品网站。
4. 如果账号里已有其他网站，请为本次网站规划新的仓库、Worker、D1 和 MEDIA_KV，保持资源完全独立。
5. 如果同一个 GPT 正在帮助不同学生，请以当前浏览器里的 GitHub / Cloudflare 登录身份为准。

公共模板配置只声明 DB 和 MEDIA_KV 绑定，不携带任何站点的真实资源 ID，也不携带固定 database_name。Cloudflare 必须按当前 Worker 名与绑定为本网站独立创建资源，并在平台支持时把精确 ID 写入本次克隆仓库的配置；同一账号的多个站点不得按固定数据库名复用 D1。首次部署后，请只读核对克隆仓库与当前 Worker 的 DB、MEDIA_KV ID 已固定且逐项一致；平台未写回时停止后续自动升级准备，只从当前站点的 Cloudflare 官方资源界面精确补回，绝不猜测或复用其他站点的 ID。Workers Builds 提供 WRANGLER_CI_OVERRIDE_NAME 时，部署检查会先验证它并作为有效 Worker 名，状态、版本、资源指纹和最终部署必须始终指向该名称。

在要求我授权前，先分别对当前 GitHub 和 Cloudflare 连接执行一次无害的只读检查。只读检查成功就复用现有连接，不要再次打开授权页面。只有官方连接明确返回 Connect、Reconnect、授权已过期或权限不足时，才让我在官方页面授权一次。授权后重新执行同一只读检查，并从刚才中断的步骤继续；不要重新开始部署，不要重复创建仓库、Worker、D1 或 MEDIA_KV。若授权页面连续再次出现，立即停止并核对账号、目标站点和已经创建的资源。

账号和命名确认完成后，再带我打开官方 Deploy to Cloudflare：
https://deploy.workers.cloudflare.com/?url=https://github.com/q1433031046-ship-it/student-portfolio-cloudflare

请自动完成能够完成的检查、构建、迁移和验证。GitHub / Cloudflare 官方授权、一次性部署口令、管理员密码和系统恢复码由我本人操作。

以下信息始终由我本人在官方页面输入，不进入聊天：GitHub 密码、Cloudflare 密码、管理员密码、INITIAL_ADMIN_CODE、系统恢复码、浏览器 Cookie、长期 API Token。

首次部署完成后继续带我进入 /admin：使用一次性部署口令创建管理员密码、保存系统恢复码，并检查图片上传、可选 MP4（上传时检查播放；留空时检查 00:00 和无播放按钮）、草稿预览、正式发布、二维码访问、网站空间、使用教程和程序升级中心。
```

### 2.4 先完成账号核对

GPT 应先确认：

- 当前正在帮助哪位学生；
- GitHub 登录身份；
- Cloudflare 登录身份；
- 这是第几个网站；
- 新站的仓库、Worker、D1、KV 命名；
- 新站资源是否与旧站隔离。

如果 GPT 尚未核对账号就进入部署，发送：

```text
请先确认当前浏览器里的 GitHub 和 Cloudflare 登录账号，并确认这是该账号里的第几个网站，再继续部署。
```

完成账号核对后再进入 Cloudflare。

## 3. Cloudflare 一键部署：逐步操作

Cloudflare 的页面可能随版本调整。页面已经自动填写的内容优先保留；系统已经自动创建的资源直接沿用本次部署结果。

### 3.1 打开官方入口

**[进入 Deploy to Cloudflare](https://deploy.workers.cloudflare.com/?url=https://github.com/q1433031046-ship-it/student-portfolio-cloudflare)**

该入口负责复制模板、创建仓库、配置 Worker，并准备本网站需要的 D1 与 `MEDIA_KV`。

本模板按 Cloudflare 免费资源组合设计，新站媒体保存在 `MEDIA_KV`，不需要启用 R2。页面如果要求开通 R2、付费套餐或订阅，先停止操作，只截取并遮挡需要核对的局部区域交给 GPT，不要直接确认付费。

### 3.2 GitHub 登录与授权

1. GPT 先使用 GitHub 官方连接执行一次无害的只读检查，例如读取当前账号可访问的仓库。
2. 检查成功：说明连接仍然有效，直接复用，不再打开登录或授权页面。
3. 只有官方连接明确显示 **Connect**、**Reconnect**、授权过期或权限不足时，才进入授权。
4. 授权前核对页面中的 GitHub 用户名；未登录时使用自己原来的登录方式。
5. 出现 **Authorize Cloudflare** 时，确认账号后只授权一次。
6. 授权完成后重新执行同一个只读检查，确认身份正确，再从中断步骤继续。
7. 不要重新开始整个部署，不要重复创建仓库、Worker、D1 或 `MEDIA_KV`。
8. 如果授权页面再次连续出现，立即停止并核对账号、目标网站和已经创建的资源。

### 3.3 Cloudflare 登录

GPT 同样应先对 Cloudflare 官方连接做只读检查；检查成功就复用当前连接，只有明确要求连接或重新连接时才打开登录页。授权完成后回到原步骤继续，不重新执行已经完成的资源创建。

使用创建 Cloudflare 账号时的原始方式：

- Google 创建：选择 Google；
- GitHub 创建：选择 GitHub；
- Apple 创建：选择 Apple；
- 邮箱密码创建：填写邮箱和密码。

出现下面提示时，返回并切换为最初的登录方式：

```text
Your account uses a different login provider
```

### 3.4 选择 Cloudflare 账号

一个登录身份可能包含多个 Cloudflare 账号。请选择当前学生自己的账号，并再次确认这是第几个作品网站。

### 3.5 “Set up your application” 页面怎么填

| 页面字段 | 处理方式 |
|---|---|
| Git account | 当前学生自己的 GitHub |
| Project name | 使用唯一名称，推荐 `student-portfolio-姓名拼音-01` |
| Repository | 创建新仓库；同名时使用 `-02`、`-03` |
| Create private Git repository | 页面提供时可勾选，让学生源码保持私有 |
| Production branch | 保持 `main` |
| Build command | 保留自动值，通常为 `npm run build` |
| Deploy command | 保留自动值，通常为 `npm run deploy` |
| Root directory | 保持 `/`、留空或保留默认值 |
| D1 database / DB | 优先自动创建；需要选择时选 **Create new**，名称可用 `项目名-db` |
| KV namespace / MEDIA_KV | 优先自动创建；需要选择时选 **Create new**，名称可用 `项目名-media` |
| INITIAL_ADMIN_CODE | 使用 Secret / 加密变量，至少 16 位，并同时包含英文字母和数字 |

公共模板只声明 `DB` 与 `MEDIA_KV` 绑定，不携带任何网站的真实资源 ID，也不携带固定 `database_name`。Deploy to Cloudflare 按当前 Worker 与绑定为本网站独立创建资源，并在适用时把精确 ID 写入克隆仓库配置；同一账号的多个站点不得通过固定数据库名复用 D1。

命名只使用小写英文字母、数字和短横线。

第二个网站示例：

```text
项目：student-portfolio-linyuan-02
仓库：student-portfolio-linyuan-02
D1：student-portfolio-linyuan-02-db
KV：student-portfolio-linyuan-02-media
```

### 3.6 确认资源隔离

每个网站独立拥有：

- Worker；
- D1，绑定名为 `DB`；
- KV，绑定名为 `MEDIA_KV`；
- 管理员密码和系统恢复码；
- 图片、视频、草稿和发布内容。

这一检查能避免不同网站之间出现内容串联。

### 3.7 设置一次性部署口令

`INITIAL_ADMIN_CODE`：

- 至少 16 位；
- 同时包含英文字母和数字；
- 建议使用随机组合；
- 填写在 Cloudflare Secret 输入框；
- 第一次创建管理员后，日常登录改用管理员密码。

### 3.8 点击 Deploy / Create and deploy

部署通常包含：

1. 创建或复制 GitHub 仓库；
2. 安装依赖；
3. 构建网站；
4. 创建或绑定 D1；
5. 创建或绑定 `MEDIA_KV`；
6. 应用数据库迁移；
7. 发布 Worker。

保持页面打开，等待明确的成功状态。

### 3.9 保存部署结果

记录以下信息：

- GitHub 仓库地址；
- Cloudflare Worker 名称；
- 前台 `workers.dev` 地址；
- 后台地址：前台地址后加 `/admin`。

部署完成后，让 GPT 做一次只读核对：克隆仓库 `wrangler.jsonc` 中的 `DB.database_id`、`MEDIA_KV.id` 必须已经固定，并与当前 Worker 的实际绑定逐项一致。若平台没有写回，先停止后续自动升级准备，再由 GPT 只从当前站点的 Cloudflare 官方资源界面读取精确 ID 并补回克隆配置；不得猜测，也不得复用其他网站的资源 ID。

```text
前台：https://你的项目名.你的子域.workers.dev/
后台：https://你的项目名.你的子域.workers.dev/admin
```

### 3.10 构建出现错误时

1. 打开当前项目的构建日志；
2. 滚动到最底部；
3. 截取最后一段红色错误并遮住秘密信息；
4. 让 GPT 修复当前项目；
5. 已经创建的 Worker、D1、KV 优先沿用，修复后重新部署。

## 4. 第一次进入后台

1. 打开部署后的 `/admin`。
2. 输入部署时设置的 `INITIAL_ADMIN_CODE`。
3. 创建管理员密码：10 至 128 位，至少包含文字和数字。
4. 再输入一次管理员密码。
5. 点击“创建管理员”。
6. 下载系统恢复码并离线保存。
7. 确认恢复码已保存后进入后台。

一次性部署口令只负责首次初始化；之后日常登录使用管理员密码。

第一次发布前打开网站首页会看到 **“网站尚未发布”**，这是正常状态。完成后台内容后，到“发布”栏生成第一份公开快照。

## 5. 后台每一栏怎么用

### 概览

- 修改浏览器标签与网站名称；
- 查看旧限制访问设置的保留状态，以及第一次静态发布成功后生成的固定网址和二维码；
- 查看作品、分类、媒体与修订数量；
- 查看发布状态；
- 查看网站空间；
- 查看程序版本与升级中心。

### 联系方式

- 修改邮箱、电话、眉题、主标题和说明；
- 上传 1:1 联系图片；
- 选择资料在左或图片在左；
- 在真实画布中拖动文字；
- 轻点画布文字直接修改内容。
- 主标题可直接输入中文；使用中文输入法选词时，Enter 不会提前结束编辑。

### 首图与文字

- 上传一张或多张首页首图；
- 调整顺序、复制或删除；
- 选择纯图片、系统排版或自由排版；
- 编辑姓名、职业标题、求职方向、个人定位和状态短句；
- 选择页面主题；
- 上传自定义字体；
- 调整作品区大标题。

### 作品分类

- 新建分类后，先填名称并保存草稿，再上传自定义过渡图；
- 修改名称、颜色和顺序；
- 使用系统过渡条或上传 8:1 自定义过渡图；
- 删除分类前，先把该分类中的作品移动到其他分类。

### 作品

- 新建作品后，先填写作品名称、选择分类并保存草稿，再上传封面或可选视频；
- 编辑名称、年份、简介、难点和解决思路；
- 上传 16:9 项目封面；
- **“成稿视频（可选）”** 可上传 MP4；留空也能发布，时长显示 `00:00`，前台不显示播放按钮。已有视频要改为无视频时，点击 **“移除成稿视频”**，再保存草稿并发布；
- 设置视频水印；
- 设置封面文字显示方式；
- 在真实封面中拖动标题、简介和项目信息，并分别检查“桌面 16:9”与手机预览的字号、位置和换行；
- 添加文字、图文混排、图片组、通栏图片；
- 图片组最多四张，可选择横图或竖图。

### 封底

- 点击“新建封底”可添加一张或多张封底图片；
- 每张封底都能独立上传、裁切、复制、排序和删除；

## 6. 图片与视频建议尺寸

图片支持 JPG、PNG、WebP、AVIF。系统会尝试转为 WebP，并把最长边控制在 2560 像素以内；优化后单张上限为 8 MiB。

| 使用位置 | 裁切比例 | 建议尺寸 | 构图建议 |
|---|---:|---:|---|
| 首页首图 | 自由裁切 | 2560 × 1440 | 主体放在中间 60%，四周预留裁切空间 |
| 联系图片 | 1:1 | 1600 × 1600 | 主体居中，四周留边 |
| 分类过渡图 | 8:1 | 2560 × 320 | 适合横向纹理、环境或大留白 |
| 项目封面 | 16:9 | 1920 × 1080 或 2560 × 1440 | 重要主体和文字放在安全区 |
| 封底 | 16:9 | 1920 × 1080 或 2560 × 1440 | 多张封底分别构图，重要主体放在中央安全区 |
| 图文混排图片 | 4:3 | 2000 × 1500 | 左右保留呼吸空间 |
| 图片组竖图 | 3:4 | 1500 × 2000 | 同组保持色调和主体比例一致 |
| 图片组横图 | 4:3 | 2000 × 1500 | 同组保持视觉风格一致 |
| 通栏图片 | 16:9 | 1920 × 1080 或 2560 × 1440 | 关键内容放在中央安全区 |
| 成稿视频（可选） | 推荐 16:9 | 1920 × 1080 | MP4、H.264 / AAC、单个不超过 50 MB |

### 视频压缩参考

- 30 秒：约 8–10 Mbps；
- 60 秒：约 5–6 Mbps；
- 120 秒：约 2.5–3 Mbps；
- 推荐 24、25 或 30 fps；
- 1080p 足够用于作品展示；
- 最终以导出文件实际小于 50 MB 为准。

网站应用空间上限为 800 MiB，达到约 700 MiB 时预警。

## 8. 保存草稿与正式发布

**编辑 → 保存草稿 → 快速预览 → 冻结候选 → 验证唯一 draft Deploy → 提升同一个 Deploy**

- **保存草稿**：更新后台草稿，公开前台保持当前版本；
- **快速预览**：快速预览会先自动保存当前修改，再打开管理员草稿；
- **正式发布**：冻结当前修订并触发一个 Netlify draft Deploy；系统从不可变地址核对完整制品，再把同一个 Deploy 提升到固定 `*.netlify.app` 地址；
- 新建作品先填名称和分类、新建分类先填名称，点击“保存草稿”后再上传媒体；每次上传或替换图片后也先保存草稿，再切换作品或后台栏目；
- 左下角显示“有未保存修改”时，保存后再离开；
- 浏览器拦截快速预览时，为当前站点允许弹出窗口。
- 发布按钮会显示媒体总量，并提醒先检查 Netlify 用量；页面不会伪造实时剩余额度。
- 第一次静态发布成功前，Worker 首页保持原行为，不显示固定二维码；成功后 Worker 根路径跳转到已验证的固定 Netlify 地址，`/admin` 仍留在 Worker。
- 构建、核验或发布失败时，上一成功 Deploy、固定链接和二维码保持不变；使用“重新核验”或“重试原发布任务”，不会因重复点击创建第二个 Build。
- `NETLIFY_AUTH_TOKEN`、`NETLIFY_DRAFT_BUILD_HOOK`、`STATIC_EXPORT_SIGNING_KEY` 只由发布角色通过 Cloudflare Secret 的隐藏渠道配置，绝不写入仓库、日志或聊天。
- 首次绑定、重新授权和回滚属于发布操作：只接受已确认的同一账号、唯一 Site、准确 Site ID/固定 URL；回滚只能切回上一已验证 Deploy，并在固定网址读回成功后更新数据库指针。

## 10. 密码、12 小时登录与恢复码

- 输入正确管理员密码后，这台浏览器保持登录 12 小时；
- 12 小时内再次点“管理”，通常直接进入后台；
- 点击“安全退出”后，当前会话立即结束；
- 同一 Cloudflare 客户网络连续输错 5 次管理员密码后，只锁定该网络的密码登录 15 分钟；其他网络不受影响；
- 高熵系统恢复码使用独立校验流程，不受密码网络锁定影响；错误恢复码不会触发密码登录锁定；
- 忘记密码时，使用最新系统恢复码重置；
- 恢复码每次使用后自动轮换，新码需要重新保存；
- 每次正式程序升级后，用升级前保存的当前最新恢复码确认一次；确认后旧码立即失效，并生成必须重新保存的新码；
- v1.2.0 完成确认后，管理员密码、恢复码和 12 小时会话不再依赖一次性部署口令；
- 管理员密码与最新恢复码分开离线保存。

## 13. 程序升级

### 升级按钮在哪里

登录后台后有两个入口：

1. **右上角“程序升级”**：点击后进入概览并定位升级中心；
2. **概览 → 网站空间 → 程序升级中心**：点击“复制给 GPT 的升级指令”。

每次登录后台时，网站会检查主模板的版本清单。发现新版本后，右上角 **“程序升级”会显示小红点**，升级中心会显示当前版本、最新版本和更新内容。配套升级指令只从版本清单指定的发布标签读取，并且必须通过项目、版本、标签和 SHA-256 校验；网络异常或校验失败时，复制按钮继续使用当前网站内置的安全指令。版本提醒只在登录后台后显示。

v1.3.1-b 自动升级只支持已有固定 D1 `DB` 资源 ID 和唯一 `MEDIA_KV` 资源 ID，且当前 Worker 使用同一组绑定的 v1.1+ 站点，或满足相同前置条件的旧站。纯 v1.0 R2-only 站点没有 `MEDIA_KV`，本版本未支持直接自动升级；GPT 必须在指纹和部署前停止，不得创建、复用或认领新的 `MEDIA_KV`，不得改动任何远端资源。R2 → KV 迁移只适用于已经满足前置条件、同时保留旧 R2 行的站点。

### 学生要做的 8 步

1. 在电脑上找到并打开本网站的“当前最新系统恢复码”文件；新版文件内的“站点”必须是当前 `workers.dev` 地址。旧文件没有站点信息时，把文件与当前网站地址放在同一个离线文件夹中。恢复码内容不要发给 GPT。
2. 在“程序升级中心”点击 **“复制给 GPT 的升级指令”**，把下方完整指令发给 GPT。
3. 先等 GPT 报告原站已有固定 D1 `DB` ID 和唯一 `MEDIA_KV` ID，且当前 Worker 使用相同绑定；缺少任一项就停止，不继续第 4–8 步。前置条件满足后，确认 GPT 已记录原分支和 commit、检查过没有未提交改动，再等它在隔离工作树验证 v1.3.1-b、用原站 `wrangler.jsonc` 记录升级前指纹、保留原资源配置并完成升级前二次指纹比对，最后通过严格升级入口完成同一站点的生产部署；发现本地改动时应先停止并做可恢复保存，中途需要账号授权时只在官方页面完成一次。
4. 回到步骤 1 核对过的原始 `workers.dev` 地址，打开 `/admin`；不要使用 GPT 发来的陌生地址。
5. 在“完成一次升级确认”页依次填写 **“当前最新系统恢复码”**、**“管理员密码”**、**“再次输入密码”**，点击 **“确认升级并进入后台 →”**。
6. 点击 **“下载恢复码”**，实际打开新文件。文件名格式为 `{hostname}-v1.3.1-b-系统恢复码-{YYYYMMDDTHHMMSSZ}.txt`；核对文件里的“站点”和“程序版本：v1.3.1-b”，再离线保存。旧恢复码和旧管理员会话已经失效。
7. 回到网页，点击 **“我已妥善保存，进入后台 →”**。当前浏览器会获得新的 12 小时管理员会话。
8. 如果“概览”出现 **“R2 → MEDIA_KV”**，先点击 **“开始逐块迁移并校验”**，等卡片显示完成后抽查图片和视频；然后让 GPT 对照升级前基线报告 Worker、地址、D1、`MEDIA_KV`、可选旧 `BUCKET`、数据数量和迁移状态。没有证据的生产检查必须写“未验证”。

符合上述前置条件的升级会保留当前 Worker 与 `workers.dev` 地址、D1 与内容、`MEDIA_KV` 与媒体、Secrets 名称、管理员身份、草稿与已发布内容、二维码、统计和管理记录。正式确认会按设计重设密码验证、轮换恢复码并撤销旧管理员会话。

`npm run deploy` 只用于 Deploy Button 首次部署。现有 Worker 在 push 后触发的 Cloudflare Builds 自动 deploy 会按设计关闭失败，它不代表升级成功，也不代替“指纹 → `npm run cloudflare:deploy`”严格升级流程。

`.wrangler/upgrade-before-fingerprint.json` 以 0600 权限独占创建，每轮升级只捕获一次，并在跨失败续跑时原样保留。文件已存在时程序会停止，不会覆盖。只有站点所有者确认已经开始全新一轮升级、旧基线不再需要时，才先把旧文件移入归档位置，再重新捕获；代理不得静默覆盖。

### 旧 R2 的条件迁移

- 这条迁移路径要求原站已经有固定 `DB` ID 和唯一 `MEDIA_KV` ID；它不会为纯 v1.0 R2-only 站点补建 KV。
- D1 没有 `storage_backend='r2'` 行：不创建、不绑定 R2，直接完成其余升级。
- D1 有旧 R2 行：保留或临时恢复这个站原有的同一个 `BUCKET`；绑定缺失或身份不明时停止。
- 后台“概览”出现 **“R2 → MEDIA_KV”** 卡片时，点击 **“开始逐块迁移并校验”**。程序会固定原 R2 对象的 ETag；每次复制一个 4 MiB 分片，并校验 R2 源与 KV 回读的字节数和 SHA-256。全部复制后进入可续跑的 `final-verifying` 最终 KV 复验，每次重读一个 KV 分片并与复制台账核对；只有全量复验通过才切换媒体状态。ETag 变化、KV 块缺失或校验不一致都会中止本次操作并保持 R2；再次点击会从已记录的阶段继续。
- 旧版已有的 50–90 MiB 视频原样保留；50 MiB 只是新上传上限。
- schema 1 的首图继续进入当前首图；已退役的初稿媒体只记入仅管理员可取的私有文档归档引用，底层媒体保留，服务端返回公开文档前会剔除该引用，不进入预览、前台或播放。
- 卡片显示 **“迁移与逐块校验已完成”**、R2 行为 0 且抽查正常后，才进入观察和解绑决策。程序不自动删除旧 R2 对象；任何解绑或删除都需要站点所有者对精确目标另行批准。

复制给 GPT：

```text
请把我的“学生作品展示”现有网站安全升级到 v1.3.1-b。目标版本固定为 v1.3.1-b；升级代码和配套指令只使用官方仓库发布标签 v1.3.1-b。先读取 README.md、AGENTS.md、deployment/agent-manifest.json、deployment/template-version.json 和 deployment/upgrade-prompt.json，并对发布标签中 upgrade-prompt.json 的 prompt 原始 UTF-8 文本计算 SHA-256；结果必须与两个发布清单记录的摘要一致，任一版本、标签或摘要不一致就停止。

这是“升级现有站点”，不是新建站点。v1.3.1-b 自动升级只支持原站配置已有固定 D1 DB 资源 ID 和唯一 MEDIA_KV 资源 ID、且当前 Worker 使用相同绑定的 v1.1+ 站点或满足相同前置条件的旧站。纯 v1.0 R2-only 站点缺少 MEDIA_KV，本版本未支持直接自动升级；发现这一情况必须在指纹和部署前停止并如实报告，不得创建、复用或认领新的 MEDIA_KV，不得改动任何远端资源。前置条件满足时，必须沿用目标站点现有 Worker、workers.dev 地址、D1 的 DB 绑定与资源 ID、MEDIA_KV 绑定与资源 ID、Secrets 和运行变量；不得创建第二套 Worker、D1 或 KV，不得把模板仓库中的任何资源 ID 覆盖到现有站点，不得要求开通付费套餐或绑定付款方式。管理员身份、媒体、草稿、已发布内容、二维码与访问凭证、统计和审计记录必须保留；正式升级确认会按设计轮换系统恢复码、重建密码验证状态并撤销旧管理员会话。

账号授权与秘密边界：开始授权前，先对 GitHub 和 Cloudflare 官方连接各执行一次无害的只读检查。连接有效就复用；仅在官方连接明确显示 Connect、Reconnect、授权过期或权限不足时授权一次。授权后重复同一只读检查，并从中断步骤继续。授权页再次出现时先停止，核对账号、目标站点和已存在资源。INITIAL_ADMIN_CODE、管理员密码、当前最新系统恢复码、Token、Cookie 只由我本人在官方页面输入；聊天中不要索取、展示、记录或写入文件。仅可让我提供遮住秘密、二维码和访问链接的局部截图。

步骤 1/8｜验证前置资源、工具并记录升级前基线。先只读检查原站 wrangler.jsonc：必须已有带 database_id 的唯一 DB 绑定和带 id 的唯一 MEDIA_KV 绑定；缺少任一项时立即判定不满足本版本升级前置条件，不运行部署，不创建、复用或认领 KV。配置满足后，在原站工作树和仓库目录之外创建指向已验证 refs/tags/v1.3.1-b 的临时 detached 隔离工作树，在其中运行 npm ci；该工作树只做读取和指纹检查，不 deploy，不覆盖原站配置。代理自行解析两个绝对路径，不让我填写路径：从任意 cwd 运行 node，以该标签工作树的 scripts/cloudflare-deploy.mjs 绝对路径为脚本，传入 --mode upgrade --inspect；脚本会把 Wrangler 的运行目录固定为已验证标签工作树根目录，使用该标签已安装的依赖。--config 指向原站精确 wrangler.jsonc 的绝对路径，--manifest 指向标签内 agent-manifest 的绝对路径，--output 固定指向原站 .wrangler/upgrade-before-fingerprint.json 的绝对路径。若环境提供 WRANGLER_CI_OVERRIDE_NAME，必须先按 Worker 命名规则验证并把它作为唯一有效 Worker 名；状态查询、版本检查、资源指纹和最终部署全程使用同一名称，非法或不一致就停止。单独记下远端 workers.dev 开关与完整地址，再核对 GitHub 仓库、Cloudflare 账户、Worker 名称、DB 与 MEDIA_KV 的资源 ID，以及已有 BUCKET 的名称和绑定（如存在）；当前 Worker 的 DB 和 MEDIA_KV 必须与配置逐项相同。记录当前版本、提交、D1 迁移清单、草稿与已发布修订、媒体数量与总字节、二维码数量。指纹核对有效 Worker 名、原站 wrangler 配置的 configuredWorkersDevEnabled 值、DB、KV、可选 R2、全部实际 Secret 绑定名称，以及运行变量的绑定名、类型和值 SHA-256（不记录变量原值）。指纹路径已被 Git 忽略，只保存在原站本地，不贴进聊天；以 0600 权限独占创建，每轮升级只捕获一次并跨失败续跑保留，已有文件必须关闭失败而不得覆盖。只有我确认已开始全新一轮升级且旧基线不再需要时，才先把旧文件移入归档位置再捕获；代理不得静默覆盖。远端 workers.dev 状态是单独的人工基线；任一正式资源无法确认就停止。

步骤 2/8｜确认恢复入口。只询问我是否已在本地保存当前站点的“当前最新系统恢复码”文件，不询问内容；让我核对文件内站点地址确属本次 workers.dev 站点。无法确认时停在任何改动和部署之前。

步骤 3/8｜更新源码并复核升级前指纹。步骤 2 确认恢复入口后，记录原分支和 commit，并确认工作树没有未提交改动；发现本地修改就停止，先以提交、补丁或独立备份做可恢复保存并取得我的确认，禁止 force checkout、reset --hard 或静默丢弃文件。然后在仓库外保存原站 wrangler.jsonc 的完整备份，再把原工作树 checkout 到步骤 1 已验证标签的精确 commit；逐字恢复原 wrangler.jsonc，保留原站 .wrangler/upgrade-before-fingerprint.json，不引入模板资源 ID，也不把 push main 当成升级手段。运行 npm ci，再运行 npm run cloudflare:fingerprint -- --output .wrangler/upgrade-predeploy-fingerprint.json，与 .wrangler/upgrade-before-fingerprint.json 严格比较；不要覆盖 before 文件。二者完全一致后，运行发布契约中的生产依赖审计、部署脚本语法、迁移漂移、npm test（含一次生产构建）、Wrangler dry-run、Lint 和 TypeScript 检查。任何检查失败先修复并重跑，不进入部署。

步骤 4/8｜检查旧数据分支。先只读检查 D1 是否有 storage_backend='r2' 的已上传媒体及 schema 1 内容。没有 R2 行时沿用 MEDIA_KV，且不得创建或绑定 R2。有 R2 行时只允许保留或临时恢复该站原有同一个 BUCKET 绑定；BUCKET 缺失或身份不明立即停止。旧版最高 90 MiB 的已有视频必须原样保留，当前 50 MiB 只限制新上传。schema 1 的 hero.media 要进入当前首图；已退役的 draftVideo 仅转为仅管理员可取的私有文档归档引用，底层媒体保留；服务端返回公开文档前必须剔除该引用，不得进入预览、前台或播放接口。

步骤 5/8｜部署到同一目标。npm run deploy 只用于 Deploy Button 首次部署；现有 Worker 在 push 后触发的 Cloudflare Builds 自动 deploy 应关闭失败，不得把它报告为升级成功或用它代替严格升级。只应用尚未执行的前向迁移，包括 0006_auth_v2.sql、0007_legacy_media_and_access_state.sql 和 0008_static_site_publish.sql；必须在步骤 3 已收敛为“已验证标签精确代码 + 原站 wrangler.jsonc”的原站仓库 cwd 执行；升级唯一入口是 npm run cloudflare:deploy。该命令会读取 .wrangler/upgrade-before-fingerprint.json，并在远程改动前复核步骤 1 的指纹。只有 wrangler d1 migrations list 已成功并可靠列出全部 pending，随后 apply 明确报告 D1 权限错误，且全部 pending 都列在 agent-manifest 的 runtimeSafeBootstrapMigrations 并通过幂等 DDL 校验时，才可先部署运行时兼容代码并在原 D1 通过 /admin 自举。list 自身失败或无法证明完整 pending，以及资源不匹配、未知迁移、SQL、配置或网络错误，都必须关闭失败。中断后先读取既有状态，从失败步骤续跑。

步骤 6/8｜完成官方升级确认。部署后回到步骤 1 记录的原始 workers.dev 地址并打开 /admin；页面应显示“完成一次升级确认”。由我本人依次输入“当前最新系统恢复码”“管理员密码”“再次输入密码”，点击“确认升级并进入后台 →”。随后点击“下载恢复码”，实际打开新下载的站点专属恢复码文件；文件名应符合 {hostname}-v1.3.1-b-系统恢复码-{YYYYMMDDTHHMMSSZ}.txt。核对其中站点地址和程序版本 v1.3.1-b，再点击“我已妥善保存，进入后台 →”。旧恢复码和所有旧管理员会话此时应失效，当前浏览器获得新的 12 小时会话。

步骤 7/8｜条件收敛旧 R2。若步骤 4 发现 R2 行，登录后台后读取 GET /api/admin/storage 的 legacyMigration，并重复调用 POST /api/admin/storage/migrate。首次读取时固定原 R2 对象 ETag；每次续跑、每个 R2 分片响应、进入最终复验前和 CAS 前都必须严格匹配同一 ETag，同 key、同大小但 ETag 变化也要中文关闭失败。复制阶段每次只复制一个 4 MiB 分片，并校验 R2 源与写入后 KV 回读的字节数和 SHA-256。复制台账完整后进入可续跑的 final-verifying 最终 KV 复验；每次重读一个当前 KV 分片，与复制台账的字节数和 SHA-256 核对。只有全部块最终复验台账完整且逐项一致后，才可用 CAS 把媒体行切换为 kv；任一 KV 块缺失或变化都要阻断并保持 r2。中断后从台账记录的阶段续跑。直到 R2 行归零、摘要为 complete、旧图片与视频首尾及抽样分片可读之前，保持 BUCKET 绑定。观察期内保留原 R2 对象；没有我对精确对象的另行明确批准，不解绑 BUCKET、不删除 R2 对象。

步骤 8/8｜对照基线并验收。运行 npm run cloudflare:fingerprint -- --output .wrangler/upgrade-after-fingerprint.json，把它与 .wrangler/upgrade-before-fingerprint.json 比较，确认 Worker、本地 configuredWorkersDevEnabled 配置值、DB、MEDIA_KV、已有 BUCKET、全部实际 Secret 绑定名称和运行变量的绑定名/类型/值 SHA-256 未被替换。再人工核对步骤 1 记录的远端 workers.dev 开关与完整地址，并核对数据计数。确认迁移清单、版本 v1.3.1-b、恢复码轮换和旧会话撤销。管理员密码限流按同一 Cloudflare 客户网络隔离：同一网络连续 5 次错误后只锁定该网络的密码登录 15 分钟；其他网络和高熵系统恢复码流程不受该密码网络桶影响，错误恢复码不会触发密码登录锁定。按真实界面检查：“联系方式”；图片“调整裁切”；新建作品和新建分类必须先保存草稿再上传媒体；“快速预览”会先自动保存当前修改；保存草稿不得触发 Netlify。正式发布必须冻结当前修订，只触发一个 Build，核验唯一不可变 draft Deploy 后提升同一个 deploy_id；失败时使用“重新核验”或“重试原发布任务”，不得因重复点击创建第二个 Build。旧限制访问卡片必须保持不可写，并确认原设置、访问码、次数、到期时间和历史记录仍被保留且不控制新的静态公开站。第一次静态发布成功前不得显示新固定二维码；成功后固定 URL、二维码和 Worker 根路径跳转必须一致，/admin 与 API 不跳转。重新发布或回滚不得更换 Site、固定 URL 或二维码，失败时上一成功 Deploy 保持在线。成稿视频可选：无视频作品可发布、显示 00:00 且前台没有播放按钮；已有视频要改为无视频时，点“移除成稿视频”并保存草稿后发布；有视频时验证播放和 Range 拖动，新上传超过 50 MiB 应拒绝，旧 50–90 MiB 媒体继续可读。保留 v1.2.0 已有的中文可选文案、输入法编辑、精确错误定位和多张独立封底行为。用独立浏览器配置文件或隔离 Cookie jar 建立 10 个独立 Cookie 会话，不用同一会话的 10 个标签页。真实资源指纹、生产数据、10 会话并发及大陆网络访问仅能在生产站人工验收；大陆手机流量和常用宽带由站点所有者实际打开检查。不能取得证据的项目标记“未验证”，不要报告为通过。手机端专项验收必须覆盖 320、360 和 390 px 宽度：前台无水平溢出，首图可触摸横向吸附，作品正文单列可读，联系、视频和封底遵守安全区；后台只有一条底部操作栏，栏目导航、更多操作、保存状态和错误定位可用，所有关键触控目标至少 44 px，输入框至少 16 px。手机快速预览必须复用当前草稿的真实作品树并能定位首图、当前作品、联系模块和封底，不得保存另一套手机坐标、裁切或文档字段。手机裁切必须验证拖动、双指缩放、加减缩放、重置、取消恢复和确认写入；上传进行中必须阻止切换栏目、预览、保存和发布，失败后应解除阻止并保留重试、关闭和定位入口。发布标签创建前必须通过 Playwright 手机 Chromium 布局与交互测试、品牌 Chrome 的 H.264/AAC 播放测试，以及独立 macOS WebKit 的 H.264/AAC 播放测试；不能运行或没有证据时必须停止发布并报告为未验证。最后报告目标版本、标签、提交、SHA-256、自动检查、真实浏览器检查、生产部署、基线对比、媒体迁移状态、人工验收结果和仍待完成事项。
```

## 14. 常见问题

### 为什么会直接进入后台

这台浏览器仍处于 12 小时登录期。点击“安全退出”后重新进入，可以验证密码门禁。

### Cloudflare 提示 different login provider

当前选择的登录方式与账号创建方式不同。返回并使用最初的 Google、GitHub、Apple 或邮箱密码方式。

### 项目名称已经存在

使用 `-02` 或 `-03` 创建新的唯一名称，并为新站配置独立 D1 与 KV。

### 构建没有成功

查看日志最底部的红色错误，让 GPT 修复当前项目，并沿用本次已经创建的资源。

### 图片上传没有完成

确认格式受支持，最长边建议控制在 2560 像素以内，优化后文件小于 8 MiB。

### 图片已经上传，但提示等待保存或预览暂时无法读取

先点击“保存草稿”，再点图片下方的“重新检查”或重新进入当前作品。不要重复上传同一张图；如果快速预览能打开而后台仍不显示，截取当前图片区和左下角状态提示交给 GPT。

### 视频上传没有完成

成稿视频是可选项。已有视频要改为无视频时，进入 **作品 → 成稿视频（可选）**，点击 **“移除成稿视频”**，再保存草稿并发布。需要视频时，确认文件为 H.264 / AAC 编码的 MP4，且小于 50 MiB；从旧版保留下来的 50–90 MiB 视频不需要重新上传。

### 快速预览没有打开

为当前站点允许弹出窗口，然后再次点击“快速预览”。

### 保存后前台仍是旧内容

保存草稿不会更新公开站。进入“发布”启动静态发布；只有同一个 draft Deploy 通过完整核验并从固定网址读回后，公开站才更新。任务仍在进行时点“重新核验”，不要重复创建发布。

### 静态发布显示需要重新授权或失败

不要把 Token 或 Build Hook 发到聊天。由发布角色核对当前学生的 Netlify 账号和唯一 Site；401/403 时重新授权，其他失败先读回原 provider request key 和 Deploy。上一成功网站继续在线。

### 使用教程或程序升级按钮未显示

确认已成功登录管理员后台，然后按 `Ctrl + F5` 强制刷新。

### 教程入口在哪里

部署前看 GitHub README；部署后从管理员后台右上角打开“使用教程”。
